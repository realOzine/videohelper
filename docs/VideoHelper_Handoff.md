# VideoHelper — 讨论上下文 Handoff

更新日期：2026-10-24  
用途：供新会话或接手者快速恢复讨论上下文。本文记录已表达的目标、讨论过的方案和当前进展，不是项目规则、开发规范或已完成系统的说明。

## 1. 用户想做什么

用户 ozine 想做一个 **VideoHelper：通用的视频 AI 助手**。用户导入或上传视频后，可以用自然语言查找画面、事件或说过的话，定位到具体时间段，再围绕视频内容问答、整理笔记、聚合分析及关联多个视频。

核心表达是：**把视频交给它，告诉它你想做什么。** 检索、转录和总结是助手的能力，而不是分别定义产品的边界。

此前讨论曾偏向“操作时遇到问题，通过教程视频找到解决方法”，并据此推荐 HowLens、StepAtlas 等名字。用户随后明确表示想实现的是 videohelper。当前定位已回到通用视频助手，教程、实验和操作步骤只是应用场景，不再代表整个产品。VideoHelper 可作当前工作名，正式品牌、域名与商标尚未确定。

讨论过的首版切入点是：导入视频 → 自然语言定位片段 → 带时间戳问答 → 整理笔记。这是助手提出的起步建议，尚未形成用户逐项确认的功能清单；自动剪辑、视频生成等也没有被确定为首版需求。

## 2. 技术方向如何收敛

讨论起点是分析 `IliasHad/edit-mind`。它提供了“视频预处理、时间片段、多个模型编码、向量检索、聊天界面”的参考。用户发现其不少模型调用用 TypeScript 实现，希望自己的项目以 Go 为主要后端和编排语言，连接 Python 使用模型。

用户明确表达的方向如下：

| 方向 | 已讨论的含义 |
|---|---|
| Go 为主要后端和编排语言 | API、业务、任务编排、搜索、Agent、存储访问主要由 Go 承担；不意味着前端和模型推理也改用 Go。 |
| Python 承载模型推理 | Go 调用常驻 Python 服务，而不是重写 PyTorch 模型。 |
| WeMM 处理文字与视频 embedding | 用户明确指定 Tencent/WeMM-Embedding，替换原讨论中的 MPNet 与 CLIP 主编码方案。图像编码是可扩展方向。 |
| CLAP 继续处理音频 embedding | 用户明确保留 clap-htsat-unfused；文字搜索声音时，也走 CLAP 的文本编码路径。 |
| AWS + Docker 部署 | 用户计划在 AWS 上使用多个容器部署，并关心模块、服务和实际部署之间的对应关系。 |

**助手建议、尚未逐项定案的细节**：HTTP + JSON、FastAPI、Asynq + Redis、PostgreSQL、Qdrant/S3、React/Next.js；WeMM-Embedding-2B 与 1024 维作为初始配置，CLAP 为独立 512 维空间；约 10 秒切片、RRF 排名融合。具体框架、存储实现、切片粒度、模型规格和资源配置仍可调整。Whisper、OCR、YOLO、BLIP 讨论过，但没有要求首版全部接入。

## 3. Go / Python 与队列：目前讨论中的方案

### 职责

Go 负责决定调用什么模型、组织处理顺序、记录业务状态、写入索引及编排 Agent。Python 负责模型加载、媒体预处理、推理和返回结果。外部 LLM API 可以由 Go 直接调用，不必经由 Python。

### 离线索引与在线查询分开

```text
离线：上传视频 → Go API 创建任务 → Redis / Asynq
      → Go Worker → Python 推理 → Go 保存元数据和向量

在线：用户查询 → Go Search / Agent → Python 编码查询
      → 对应向量索引召回 → 结果融合与时间片段回查
      → 返回片段，或由 Go 调用 LLM 组织回答
```

首版通信建议是 **Go Worker + HTTP/JSON + Python FastAPI**，Asynq 管理后台任务。在线查询直接请求模型服务，不必进入离线队列；Agent 调 LLM 也不必全部经过 Worker。

四种通信方式已比较过：HTTP/JSON 易实现、易排障；gRPC 的类型契约、流式通信有价值，但暂未出现必须采用它的需求；WebSocket 能双向推送，不过会增加重连、任务关联和恢复复杂度；消息队列解决持久化排队、重试和调度，与前面三种通信机制不是同一层面的四选一。Kafka 也讨论过，当前没有决定引入。

用户专门追问过“为什么 Python 不能直接消费 Asynq”。讨论结论是：并非技术上不可能，而是 Asynq 的任务封装、状态迁移、租约与重试不是普通 Redis 队列接口。当前方案由 **Go Worker 消费 Asynq，再调用 Python**，避免维护 Python 对其内部协议的兼容实现。

已意识到的限制包括：同步等待推理会占用 Worker 并发槽；网络超时不代表 Python/GPU 已停止计算；任务重试可能造成重复执行。因此幂等、任务恢复、取消和 GPU 并发限制仍是后续设计议题，不是已实现能力。

## 4. 模型与检索的关键上下文

讨论采用两个独立的检索空间：

```text
WeMM：文字查询 ↔ 视频片段 / 文本内容（图像后续可扩展）
CLAP：声音描述文字 ↔ 音频片段
```

两路向量各自在对应空间检索，候选结果再按 `scene_id` 与时间范围关联。它们不能因为都是向量就直接互相比相似度，即使将来维度碰巧相同也不代表空间兼容。RRF 是讨论过的融合起点，不是最终算法承诺。

片段拟保留 `video_id`、`scene_id`、`start_ms`、`end_ms` 等信息，用于播放回跳和回答引用。模型版本、维度及预处理配置也讨论过需要随索引记录；变更模型可能涉及重新编码。

约 10 秒片段是初始实验建议，不是 WeMM 的固定输入限制或最佳粒度结论。完整事件和步骤可能需要拼接或扩展相邻时间范围。CLAP 的声音语义也不等同于逐字转录；Whisper/字幕仍是另一类证据。

WeMM 的查询/文档编码封装、真实模型加载、中文检索、时序定位效果、显存、延迟与吞吐均未完成真实验证。没有证据可以据此承诺它可靠理解所有动作过程。

## 5. 用户要求的三种架构视角

| 视角 | 用户真正想看到的内容 |
|---|---|
| Code View | 源码目录、package/module、模块职责和依赖，例如 API、Worker、search、agent、模型客户端与 Python 模型目录。 |
| Deploy View | AWS 上实际运行在哪些主机/容器、哪些是外部或托管资源，以及连接关系。 |
| Logic / Service View | 以服务职责描述谁调用谁，例如项目/视频、搜索、Agent、索引、模型服务，并标注通信协议。它不等于目录图。 |

三种视图都已生成过。后续讨论补充：代码文件夹、Go module、逻辑服务、运行进程和容器不必一一对应。单 Go module、多 package、API 与 Worker 分进程是助手建议，并不是用户要求每个服务都拆开部署。

协议讨论中，浏览器侧为 HTTPS/JSON，可用 SSE 返回进度；Go → Python 首版倾向 HTTP/JSON；Go 内部模块是函数/接口调用。Redis、数据库、向量库与对象存储的具体协议取决于选型，原图中的“SQL”“SDK”是简写。

已有 AWS 图中出现过 ALB、ECS、ECR、RDS、ElastiCache、S3、Qdrant 和多副本。它们是示意方案，不是部署事实或已确定采购清单。后续又建议过 CPU/GPU EC2 分开、Docker Compose 起步。最终实例、区域、预算、GPU 配额与部署形态尚未确定。共享本地目录适用于同机示例；跨主机媒体读取讨论过用 S3 等对象存储。

## 6. 当前实际产物与完成程度

已有 `wemm-clap-go-starter.zip`：Go API、Go HTTP 模型客户端、相似度 demo、Python FastAPI 的 WeMM/CLAP 接口、Dockerfile、Compose/GPU 示例和测试。它是 **模型接入原型**，不是完整视频平台。[1]

原型尚未包含完整上传鉴权、Asynq 流水线、业务数据库、向量数据库检索或产品前端。真实权重推理、检索质量和 AWS 部署没有验证。[1][2]

先前交接记录报告 Go 单元测试、Python 语法检查和 4 个 Python Mock 测试通过；这些不证明模型效果、Docker 构建或 GPU 可用。本次仅压缩上下文，没有复跑测试。[2]

另有三种架构图，以及旧版 `Video_Agent_Handoff_v1.0.md/.docx` 和 `Video_Agent_Handoff_Pack_v1.0.zip`。旧版写得较长，含技术规范、里程碑与接手指令，并仍偏教程/操作经验定位。用户此次要的是精简上下文 handoff，而不是进一步形成项目规则。

没有已确认的正式项目仓库、AWS 部署结果或完整产品实现。讨论中的结构和能力不能作为代码已经存在的依据。

## 7. 讨论停在哪里

产品方向已澄清为通用 VideoHelper；Go + Python、WeMM + CLAP、AWS + Docker 是主要背景。接下来可以继续讨论产品能力、验证真实模型或推进原型，但具体工作尚未在本次请求中指定。

仍开放的问题包括：首版功能的精确范围、最终模型版本与资源需求、向量库和前端框架、切片/融合策略，以及 AWS 成本与部署选择。此前建议先跑通真实视频的编码与检索，再扩展完整上传、异步索引和 Agent 闭环；该顺序是建议，不是交接指令。
